🚀 What's New

🧩 v14.0.0 — a snapshot carries values, not machinery (August 2026)

One question turned out to be behind four separate bugs, and nothing in the codebase had ever forced anyone to answer it: what part of a marker is state? A snapshot exists to rehydrate a tree that already knows how to derive things — not to reconstruct one from scratch. Anything recomputable is structure, and structure does not belong in a payload.

💥 Breaking

  • Calling a leaf is no longer a setter. tree.$.count(5) is a compile error. A leaf is a real Angular signal, so calling it is a READ that discards the argument — it never wrote anything, at any version. It type-checked and then silently did nothing, which is the worst pair of failure modes available. Use .set() / .update() ; branches and the root stay callable, unchanged.
  • @signaltree/callable-syntax is deleted. The build transform that was meant to make the line above real could not run inside an Angular app at all — @angular/build:application exposes no plugin hook, and by the time the experimental one runs, the Angular compiler has already claimed every .ts file. It also could not tell a leaf from a branch, so it rewrote branch calls into .set() on an accessor that has no such method. Its /augmentation entry re-introduced the exact @ngrx/signals conflict core had deliberately removed.
  • Snapshot payloads changed shape (format 2.0.0 , now written into the payload). Markers emit values instead of their API surface — status() no longer ships six computeds and nine setter methods into a payload that then threw on restore, and entityMap no longer emits a map that JSON.stringify renders as {{ '{}' }} while holding 10,000 entities.
  • The unexported asyncStream marker is removed. Accumulation is three lines of composition over a plain leaf, and a leaf is captured by timeTravel(), appears in tree() and persists with no marker contract to satisfy.

🐛 Fixed — data that was silently disappearing

  • Undo/redo actually works on markers. Previously an undo left a marker at its post-change value and reported success, landing you in a state that never existed. Measured before the fix: n=3 rows=3 → undo → n=2 rows=3.
  • Form state survives a round trip. form() and the three async markers vanished from every snapshot entirely. touched is now restored on undo and deliberately dropped on rehydrate; submitting is never restored, because nothing is in flight after a process boundary.
  • A loader-backed collection is no longer clobbered by rehydration. The marker that knows least about freshness used to be last to write. Now a marker that owns a source declines a tree-level rehydrate — and the knob for offline-first already existed (persist: {{ '{' }} hydrateThenRevalidate {{ '}' }}).
  • Scrubbing a devtools timeline no longer rewrites your localStorage. Undo and devtools replay were indistinguishable because both tagged writes 'time-travel'. Undoing should write through to storage; dragging a devtools slider should not.
  • stored() can no longer leak its storage adapter into a snapshot — a security fix, not a tidy-up.

🔊 New diagnostics — making the silence loud

  • ST2022 — a custom marker registered without saying what of it is state. Checked at registration, because the materializer swallows throws and a guard there fails open.
  • ST2023 — a marker that can be snapshotted but never restored. It serialises perfectly and discards every write, and ST2022 cannot see it because a snapshot hook is a valid answer to the question ST2022 asks.
  • ST2020 (two stored() markers racing on one key) and ST2021 (a marker inside an array, which is never traversed and so never materialises).

📐 Marker authoring

  • The marker registry now has both halves. A processor declares snapshot and hydrate alongside check and create , and hydrate receives the mode — merge (a partial write), restore (undo/redo, same process), or rehydrate (a process boundary was crossed). Mode is a property of the call site, the only place that knows. The rule that falls out: restore is exact, rehydrate is opinionated.

⚡ v13.5.0 — tree() rebuilds only what changed (August 2026)

Reading the whole state used to cost O(state) every single time, even when one leaf had changed and even when nothing had. That is the full-state-work-per-change pattern this library exists to avoid — the video-frame principle, applied to state: you don't re-encode every pixel because one moved.

⚡ Performance

  • tree() is memoised and structurally shared. A node rebuilds only when a signal beneath it actually changed; clean subtrees come back by reference. Reading the whole state after a one-leaf write went 1807.8µs → 149.2µs on a 10,000-leaf tree, and reading it with nothing changed returns the identical object in 0.044µs. Built on Angular's own computed(), so the invalidation rides the existing write path and costs writes nothing.
  • timeTravel() no longer scales with state size. A history entry is now the snapshot reference rather than a structuredClone, and every comparison collapses to ===. 50 writes each changing ONE number, at 10,000 rows: 340.60ms → 0.04ms. Flat in state size — that is the qualitative change, not the percentage. Memory per entry drops from a full copy of state to only the nodes that changed.
  • Serialisation stopped stringifying the tree to ask "did anything change?" autoSave polled JSON.stringify(tree()) every 100ms to answer a yes/no question the write path already knew. It is now an O(1) identity check.

✨ New

  • compared() / byKeys() — per-leaf equality. A tree has one equality function for every leaf, which is the right default and the wrong answer for a few positions: it cannot know which fields matter, or that a version field already answers the question.
    user: compared(initialUser, byKeys<User>('id', 'version'))
    On an object leaf that is 53.8ns → 8.9ns, and on the same object re-fetched over HTTP (equivalent value, new identity) 110.3ns → 9.0ns. The point is not the speed: a comparator reaches the reference-equality floor while keeping re-fetch correctness, which is exactly why defaulting leaves to Object.is stays wrong.
    Not for primitives. deepEqual's first line is already the fast path — on a changing number it beats Object.is 6.5ns to 8.1ns. There is nothing to specialise.
  • [ST2018] — a warning when a collection is stored as a plain array leaf. The most expensive idiom mistake available here, and it does not look like a mistake. 1000 updates to a 50,000-row collection: 49.80ms as an array leaf versus 1.63ms via entityMap — the array leaf lands at parity with the immutable stores SignalTree otherwise beats ~28x. Documentation did not prevent this: our own demo benchmark shipped the array-leaf idiom while the entity cookbook sat in the repo. Hence a diagnostic instead of another guide.

🐛 Fixed

  • A held byId() reference died permanently across remove → re-add. The node captured the per-entity signal once, so a re-added entity left the held reference reading an orphan forever. Holding a reference to a nested position is the capability this library has and immutable stores do not — it has to survive the collection churning underneath it.
  • timeTravel() charged you for other people's trees. It subscribes to the global flush, so every time-travelled tree materialised and deep-cloned itself whenever any tree in the process flushed: 0.008ms → 9.7ms as three unrelated 10,000-leaf trees were kept alive.

⚠️ Breaking

  • tree() no longer returns a freshly allocated object. Mutating a snapshot would corrupt the cache and survive into every later read. Snapshots were always meant to be read-only; that is now load-bearing, so each node is frozen in dev and a mutation throws immediately. If you mutate a snapshot, copy it first. Nothing in this repo did — all 751 pre-existing core tests passed with the freeze active.
  • getHistory() returns entry states by reference. The entry objects are still copied, so history metadata cannot be rewritten.

🔍 v13.4.0 — markers are visible to the tree's own snapshot and write paths (August 2026)

A durability release invites people to snapshot state — and doing that revealed the tree could not see its own markers. Two independent causes, both fixed here, plus the diagnostics that would have surfaced them years earlier.

🔐 Security

  • An explicit storage: option no longer reaches snapshots. A stored() marker nested under an object parent used to surface as its raw marker from tree(), carrying options.storage with it — and unwrap deep-copied that storage object, enumerating unrelated keys into the snapshot. Anyone passing storage: explicitly and using serialization(), persistence(), devtools or createAuditTracker was emitting that storage's contents into those payloads. The default path was never affected.
    Still open: a marker inside an array or a Map is not traversed, so it still leaks. Don't put markers in arrays or Maps.

✨ Fixed

  • stored() is now a real Angular signal. It was a plain callable satisfying neither isSignal nor the node-accessor guard — and every traversal in the library branches on exactly those two. So a top-level stored leaf was missing from tree(), a merge write through a parent was silently dropped, and applyState() (the devtools replay path) replaced the live signal with a raw value, after which reading it threw.
  • Nested markers no longer emit their raw marker object. A node accessor copies its store's properties while its call path closes over the original store; materialization only wrote to the accessor. This hit every marker — nested status(), entityMap(), form() and asyncSource() all leaked raw markers into tree(). Only stored() got noticed, because its marker carries a Storage handle.
  • tree() called before tree.$ now finalizes. Every other entry point did; the builder's own call path was the sole omission, so tree() as a first operation returned raw markers.

🆕 Added

  • Dev-mode diagnostics for writes and snapshots that go nowhere — ST2008 (a value omitted from a snapshot), ST2009 (applyState replacing a live value), ST2010 (a write to a key absent from the tree's initial shape — it has no signal to land on and is discarded), and ST2011 (a marker inside a lazy() tree, which is never materialized). All four were previously silent. ngDevMode: false removes them entirely.
  • reload() returns 'ok' | 'default' | 'error' (was void). 'error' means the stored data couldn't be read or migrated: the signal falls back to its default while storage is left intact, because destroying data a human might still recover is your call, not the library's.

⚠️ Changed (behavior)

  • Stored leaves now appear in tree()/unwrap() output, and a merge write through a parent reaches them — so it also writes to storage. A merge replaces an object-valued stored leaf rather than merging into it, where a plain nested namespace would deep-merge. Persisted values now also flow into time-travel and devtools payloads. 
// reload() now tells you what it found
const outcome = tree.$.settings.reload();
if (outcome === 'error') {
  // unreadable or unmigratable — storage was left untouched
}

// A snapshot now contains stored values instead of omitting them
tree();  // { settings: { theme: 'dark' } }  — not a raw marker

🧪 v13.3.1 — correctness follow-up to the durability release (August 2026)

An independent audit of 13.3.0 found two real defects in the work that release shipped — one of them undermining the exact guarantee it was written to provide. 13.3.0 is deprecated on npm; take this patch if you use stored() with version/migrate, or create and destroy trees.

✨ Fixed

  • clear() and reload() are no longer undone by a migration re-persist. A migrated value is written back in a queued microtask, which the timer cancellation couldn't reach — so clear() in the same tick that a tree materialized with a version migration removed the key, and one microtask later the migrated value was written straight back. That is precisely the signal/storage drift 13.3.0 claimed to eliminate.
  • The lifecycle-drain registry no longer retains destroyed trees. It held every debounced signal's flush closure forever — and through it the Storage backend, the default value, the current value and your callbacks (~4 MB measured across 20 short-lived trees). Membership is now scoped to pending writes: a signal enrols when a write is armed and leaves when it commits or is cancelled.
  • One failing signal no longer abandons the rest of a drain, and removal failures report operation: 'remove' instead of 'write'.
  • createFormTree(): field lookups no longer resolve Object.prototype members (a field named toString returned the inherited method where an error message belonged), per-index errors under a glob validator resolve, and the per-path cache is bounded.

💾 v13.3.0 — stored() writes are durable: flush(), lifecycle drain, cancel-on-clear (August 2026)

A field report from a Capacitor app: select a value, background the app within ~100 ms, and the selection is gone — the debounced storage write never fired and nothing drained it. The debounce/coalescing model was right; draining was missing. This release closes the loss window automatically and fixes two real bugs the investigation surfaced.

✨ Fixed

  • clear() and reload() cancel the pending debounced write — previously clear() removed the key but left the write timer armed, so the cleared value was written back ~100 ms later: resurrected in storage while the signal held the default. reload() had the mirror hazard (a stale pending value overwriting what was just read).
  • reload() runs migrations — it used to apply stored data regardless of its __v, so reloading a key written by an older app version (say, another tab) bypassed the migrate function initial load would have run. Reload and init now share one load path.

🆕 Added

  • Automatic lifecycle drain — every stored signal with debounced writes is flushed on visibilitychange → hidden and pagehide (one lazy listener pair, SSR-safe). By the time a mobile WebView is suspended or a tab closes, pending values are in storage — no consumer changes needed.
  • .flush() commits one signal's pending write synchronously; flushAllStoredSignals() drains everything — wire it to native lifecycle hooks the DOM can't see, e.g. Capacitor's App.addListener('pause', …).
  • maxWaitMs — plain debouncing resets the timer on every update, so a key updated faster than debounceMs never persisted until updates stopped. maxWaitMs bounds that staleness.
  • onError (+ StoredErrorContext) — storage failures (quota, serialization, migration) previously only console.warn'd in dev and were compiled out of production builds: silently dropped data. Now there's a programmatic hook.

⚠️ Changed (behavior)

  • debounceMs: 0 writes synchronously in the caller's stack (was deferred one microtask) — set() returning now means the value is in storage, for keys that must never sit in a debounce window. 
// Durability levers, least → most aggressive
tree.$.truckId.flush();                  // commit this signal's pending write now
flushAllStoredSignals();                 // drain all (e.g. Capacitor 'pause' hook)
stored('truckId', null, { debounceMs: 0 }); // synchronous per-key

// And the automatic one: backgrounding the app drains everything — no code.

🎯 v13.2.0 — typed .computed() slices, branded form errors by default (July 2026)

A shipped primitive stopped requiring a cast, a two-release-old promise got kept, and a silent failure became a loud one.

✨ Fixed

  • entityMap().computed() slice names are typed on tree.$ — reading a slice used to mean throwing away type safety with (tree.$.users as any).active(), which the docs taught as the official pattern. The runtime always worked; the types were dropped at materialization. Now tree.$.users.active() is Signal<User[]> with no cast, .computed() chains type each name independently, and loader-backed collections keep their loader surface alongside the slices. Delete those casts.
  • DevToolsMethods / OptimizedUpdateMethods are exported — they existed but were missing from the barrel, so a library wrapping an enhancer chain could not name its own return type and had to erase .batch()/.undo() for its callers.

⚠️ Changed (behavior)

  • signalForm(): nativeErrors now defaults to true — built-in validator failures arrive as Angular's branded error classes rather than plain { kind, message } objects. This is the flip announced in 11.6.0 and deferred through 12.x and 13.x. kind and message exist on both shapes, so most code is unaffected; narrowing on the plain shape, serializing errors, or deep-equalling them in tests is what changes. Pass { nativeErrors: false } to keep the old shape.

🛡️ New guardrail

  • [ST2007] — .derived() used to drop any value it didn't recognize as a signal, silently. The usual cause is brutal to find: two copies of @angular/core mean two Symbol(SIGNAL)s, so isSignal() inside SignalTree rejects a computed() you just created and every derived value vanishes. It now says so, and names the bundler fix.

📉 Bundle

  • Dev-only guardrails don't tree-shake on their own — ngDevMode is a runtime global, so the branch survives minification. Define it ("define": { "ngDevMode": "false" }) and reclaim ~0.5–0.9 KB gzip. Thrown-error messages stay on purpose. 
// Typed slices — no cast since 13.2
plants: entityMap<PlantDto, string>({ selectId: (p) => p.url })
  .computed('byUrl', (all) => Object.fromEntries(all.map((p) => [p.url, p])))
  .computed('activeCount', (all) => all.filter((p) => p.active).length),

store.$.plants.byUrl();       // Signal<Record<string, PlantDto>>
store.$.plants.activeCount(); // Signal<number>

v13 wrote down the rule for what belongs in which package — independent dependency or runtime → its own package; a within-tree mechanic → core — and moved the two capabilities that were filed wrong.

🎯 v12.1.0 — idle()/settled() status predicates + persist.maxScopes (July 2026)

Two gaps closed from external audits: a status() guard predicate that actually covers the Error state, and storage garbage collection for high-cardinality scoped loaders.

✨ New

  • status().idle() / status().settled() — the standard composite predicates. idle() is !loading() && !loaded(), true for both NotLoaded and Error — guards/resolvers should use idle(), not notLoaded(): a notLoaded()-gated fetch silently never retries after an error, because the collection has moved to the distinct Error state. settled() is loaded() || hasError() ("done, stop the spinner"); idle() and settled() deliberately overlap while errored.
  • persist.maxScopes — persisted-scope garbage collection for scoped cache-aware collections (entityMap({ load: loader(fn, { persist }) })). Each scope persists under its own storage key, so high-cardinality scopes (tenants, customers, searches) previously accumulated entries forever. With maxScopes set, the loader keeps a touch-ordered index and evicts the least-recently-written scopes beyond the cap on every write-through. Unset = previous behavior (no GC). 
// idle() vs notLoaded() after an error
store.$.orgStatus.setError(err);
store.$.orgStatus.notLoaded();  // false — WRONG guard, never retries
store.$.orgStatus.idle();       // true  — RIGHT guard, covers NotLoaded + Error

// persist.maxScopes: bounded storage for scoped loaders
customers: entityMap<Customer, string, { tenantId: string }>({
  selectId: (c) => c.id,
  load: loader(({ tenantId }) => api.getCustomers$(tenantId), {
    persist: { adapter, key: 'customers', maxScopes: 3 },
  }),
}),

📡 v11.2.0 — entityMap() cache-aware loading + invalidateTag() (July 2026)

A cache-aware, self-loading entityMap: the marker family gains a collection primitive that owns its own fetch, freshness, and invalidation — no more hand-wiring asyncSource + entityMap + manual staleness bookkeeping for the common "load a list, cache it, invalidate on demand" shape.

✨ New

  • entityMap<E, K>(config) with a load option — the full entityMap surface (all CRUD + query signals) now composes with a loader, load status, and cache semantics directly. .load() is guarded: a no-op while fresh or already in-flight, so concurrent callers coalesce onto one fetch. .refresh() forces a reload; .invalidate() marks the collection stale without fetching.
  • staleTime — freshness window (ms or a duration string like '30m') that .load() respects before refetching. swr (stale-while-revalidate) keeps loaded() true during background revalidation instead of flipping back to loading.
  • tags + invalidateTag(tree, tag) — register a collection under one or more tags, then invalidate every collection carrying that tag from anywhere with a single call. The push-invalidation seam for SSE/SignalR: an incoming "plants changed" event becomes invalidateTag(tree, 'plants'), no manual fan-out to each consumer.
  • Optional offline-first persistence — persist: { adapter, key, hydrateThenRevalidate } seeds rows instantly from a storage adapter on materialize, then revalidates via load() in the background. 
const tree = signalTree({
  plants: entityMap<PlantDto, string>({
    load: () => plantApi.list$(region),
    selectId: (p) => p.url,
    staleTime: '30m',     // skip refetch while fresh
    tags: ['plants'],     // invalidateTag(tree, 'plants')
  }),
});

tree.$.plants.all();        // PlantDto[] (full entityMap surface)
tree.$.plants.loading();    // Signal<boolean>
await tree.$.plants.load(); // guarded — no-op while fresh / in-flight
invalidateTag(tree, 'plants'); // marks every 'plants'-tagged collection stale

💥 v11.0.0 — Deprecations removed; tree-shakeable by default; linked() (June 2026)

The cleanup release the v10.3 deprecations pointed at, plus a real bundle-floor reduction and one new primitive.

⚠️ Breaking Changes

  • Deprecated is-prefix predicates removed. Use the v10.3 canonical bare names: status → loading / loaded / hasError / notLoaded (was isLoading / isLoaded / isError / isNotLoaded), and entityMap().empty (was isEmpty). All mechanical — TypeScript flags every call site.
  • Root tree.state accessor removed. Read (and write) through tree.$ everywhere — state was always the same reference, now retired.
  • security and lazy signals are opt-in. Wrap security config with security() from @signaltree/core/security, and inject lazy: lazy() from @signaltree/core/lazy to restore auto-lazy behavior. Both were statically reachable before and shipped in every bundle; they now tree-shake out when unused. Reads/writes are functionally identical.

✨ New

  • linked(...) — derived-but-writable signal. Wraps Angular's native linkedSignal: a value computed from a source that you can also write directly, re-deriving when the source changes (e.g. a "sticky selection"). Composes with serialization / persistence / snapshot. 
    // simple form
tree.derived($ => ({ doubled: linked(() => $.count() * 2) }));

// source + computation form (writable, re-derives on source change)
tree.derived($ => ({
  selected: linked({
    source: () => $.options(),
    computation: (opts, prev) => prev?.value ?? opts[0],
  }),
}));

tree.$.selected.set(next); // type-checks — it's a real WritableSignal
  • defineStore(factory, config?) — wraps a signalTree(...) factory in an injectable Angular service (inject(MyStore) resolves to the real tree; destroy() is tied to the host injector via DestroyRef). Tree-shakes out when unused.

📦 Bundle

Injecting the security + lazy/memory machinery drops the bare-tree gzip floor ~29% (7.5KB → ~5.3KB; ~8.1KB with entityMap in use), and devTools() now fully strips from production builds. Same release also corrected an old, false "smaller than NgRx SignalStore" claim — SignalStore is ~2.3KB and SignalTree is larger; the honest framing is capability-per-KB and zero runtime dependencies, not raw size.

🎯 v10.3.0 — Marker accessor shape UNIFIED (bare-name predicates) (May 2026)

A real DX bug the v10.2 benchmark surfaced: SignalTree's own markers named their predicate accessors inconsistently — status() used is-prefix (.isLoading()), entityMap had .isEmpty(), while form/asyncSource/asyncQuery already used bare names. v10.3 makes bare names canonical everywhere, matching FormControl.dirty / .valid and Angular signal conventions. 

tree.$.load.loading();   // was .isLoading()
tree.$.load.loaded();    // was .isLoaded()
tree.$.load.hasError();  // was .isError()
tree.$.users.empty();    // was .isEmpty()

No breaking changes in v10.3 — the is-prefix names became @deprecated aliases returning the same Signal instance (no double allocation), and were removed in v11.0. The deeper takeaway: the AI-codegen benchmark didn't just measure AI accuracy, it surfaced a genuine DX bug — AI-friendly and human-friendly turned out to be the same thing.

✨ v9.5.0 — Async markers: asyncSource and asyncQuery (May 2026)

The SignalTree-native answer to async state. Two new markers in the same family as entityMap, status, stored, and form: attach at any tree path, auto-derive data/loading/error signals, no manual tap()/setLoading() wiring.

✨ New

  • asyncSource<T>(config) — load-and-expose. Auto-loads on materialization. Exposes data, loading, error, plus refresh / set / update / reset. Accepts Observable or Promise loaders.
  • asyncQuery<TInput, TResult>(config) — input-driven debounced query. Writable input signal drives a debounce → filter → distinctUntilChanged → switchMap pipeline. Race conditions, cancellation, dedup all handled.
  • Live demo: /async

⚠️ v6.0.0 — Breaking Changes (summary)

SignalTree v6 tightens types and makes enhancers opt-in. Important user-facing changes (short summary):

  • Enhancer factories renamed: Short factories are now primary (e.g. persistence()); legacy withX() names remain as deprecated aliases.
  • Methods are added by enhancers: The base tree no longer declares all methods — apply an enhancer to gain its methods (e.g. time-travel, batching). This makes the type system reflect runtime behavior.
  • Polymorphic enhancer pattern: Enhancers are now polymorphic in the tree state type so TypeScript correctly infers updated APIs when you call .with().
  • Marker-based entity API: Use entityMap() in your initial state (marker) and access reactive CRUD via store.$.myEntities.*.
  • Typing & API cleanup: Removed index-signature workarounds and improved inference—prefer annotating initial values with per-field assertions (see Preferred Typing docs).

See packages/core/UPGRADE_TO_V6.md and ENHANCER_TYPE_SYSTEM_V6.md for the full migration guide and examples.

🔥 v5.0.0 (December 2025) - Major Release

⚠️ Breaking Changes

  • Middleware System Removed: The entire middleware system has been deleted. Use tap() and intercept() hooks on entity signals instead for lifecycle observation.
  • subscribe() throws outside injection context: Calling tree.subscribe() outside Angular's injection context now throws an Error instead of silently failing. Enhancers use polling fallback when needed.

✨ New Features

  • PathNotifier System: Internal notification system for path-based mutations. Enables entity hooks without global state.
  • Entity Hooks - tap(): Observe entity mutations (add/update/remove) after they occur. 
    store.$.users.tap({
  onAdd: (user, id) => console.log('Added:', user),
  onUpdate: (id, changes) => console.log('Updated:', id),
  onRemove: (id, user) => console.log('Removed:', user),
});
  • Entity Hooks - intercept(): Block or transform mutations before they happen. Perfect for validation! 
    store.$.users.intercept({
  onAdd: (user, ctx) => {
    if (!user.email.includes('@')) {
      ctx.block('Invalid email');
    }
  },
  onUpdate: (id, changes, ctx) => {
    ctx.transform({ ...changes, updatedAt: new Date() });
  },
});
  • Marker-Based Entity System: Type-safe EntityMapMarker<T, ID> with reactive CRUD operations via store.$.field.method()
  • Enhanced Types: Recursive inference up to 20+ nesting levels with improved IntelliSense
  • Angular 20.3 Support: Full compatibility with signal forms using connect() and toWritableSignal()
  • Tree-Shakeable Audit: Import audit tracking separately via @signaltree/ng-forms/audit

🚀 Performance Improvements

  • 2-5x faster bulk operations with diff-based updates in enterprise enhancer
  • 40.5% bundle size reduction with consolidated architecture and shared dependencies
  • Zero polling in Angular: subscribe() uses Angular effects when available, falling back to polling only in tests

*The speed and bundle figures above were measured on one app's workload at the time of the v5 release; your results will vary. See the current benchmarks for up-to-date, reproducible numbers.
