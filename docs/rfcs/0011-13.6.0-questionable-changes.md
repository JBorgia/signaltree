# RFC 0011 — Options analysis for the questionable 13.6.0 changes

Four changes in 13.6.0 were judgement calls rather than obvious fixes: each
changes observable behaviour, and each had plausible alternatives. This document
enumerates those alternatives, says which was chosen and why, and records the
traps — the options that look right and are not — so they are not re-proposed.

Same format as [RFC 0008](./0008-post-13.3-open-items.md).

---

## 1. `entityMap` snapshots emitted derived views

**The problem.** An entityMap node exposes `all`, `ids`, `count`, `map` and
`empty`. `tree()` emitted all five. Only `all` is state:

- `ids` duplicated every key — **48,891 bytes of a 486,733-byte snapshot** at
  10k rows, ~11%.
- `map` is a `Map`, which JSON cannot represent, so it serialised as `{}`. A
  persisted snapshot claimed the collection was **empty** while holding 10,000
  entities. That is wrong data, not just waste.
- `count` and `empty` are one deref of `all`.

`applyState` — the restore path — reads **only** `snapshot.all`.

**Options considered (13).**

1. **Do nothing.** The bloat is 11% and the `map` lie has apparently never been
   reported. Rejected: a snapshot that misreports a collection as empty is a
   correctness bug, and snapshots feed persistence and audit logs.
2. **Emit only `all`.** ← **chosen**
3. **Emit the bare entity array** — `tree().rows` becomes `Entity[]`. Cleanest
   conceptually and the biggest break: every `snapshot.rows.all` consumer and
   `applyState`'s detection both change. Deferred to a major.
4. **Emit `all` + `ids`, drop the rest.** Keeps the redundancy that costs the
   most and drops the parts that cost nothing. Backwards.
5. **Encode `map` as entries** (`[[k, v], …]`) so JSON round-trips it. Fixes the
   lie, doubles the payload. The map is derivable from `all`; paying twice to
   transmit it is the opposite of the fix.
6. **A `toJSON()` on the entityMap node.** Only affects `JSON.stringify` —
   `tree()` itself, devtools, audit and any non-JSON consumer still see all
   five. Fixes the symptom on one path.
7. **Make the derived views non-enumerable on the built snapshot.** Genuinely
   attractive: `JSON.stringify` and `Object.keys` skip them, so the payload
   shrinks and the `map` lie disappears, yet `snapshot.rows.count` still _works_
   — a strictly smaller break. **Measured and rejected:** the values must be
   computed eagerly to be present at all, and `ids()` + `count()` on a 10k
   collection cost **+12.2 µs against 14.7 µs** for entities alone — 83% added
   to every materialisation, to preserve properties that may never be read.
8. **Non-enumerable lazy getters** instead of eager values. Removes the 12.2 µs
   and introduces a worse bug: a getter reads _current_ state, so an old
   snapshot would report today's ids. A snapshot that changes after you take it
   is not a snapshot. **Trap.**
9. **A `snapshotViews: boolean` config option.** Moves the decision to the user,
   who has no way to know which of their consumers read `.ids`. Config as a
   substitute for a decision.
10. **Emit `{ all, __entityMap: true }`** so restore can detect the shape
    without duck-typing `setAll`. Worth doing on its own merits, but orthogonal
    — `applyState` already detects it correctly.
11. **Fix in `serialization()` only,** leaving `tree()` unchanged. Leaves
    devtools, audit and persistence — every other consumer — with the wrong
    data.
12. **Deprecate in 13.6, change in 14.0.** Correct process for an API removal.
    This is a snapshot that reports `empty` for a full collection; shipping a
    known-wrong payload for a whole major to be polite is the wrong trade.
13. **Keep all five and document that `map` is unreliable.** Documenting a lie
    does not stop it being logged.

**Recommendation: option 2.** Restore already reads only `.all`, so the round
trip is unaffected (verified before and after). Snapshot drops 486,733 → 437,798
bytes and stops misreporting. A consumer that wants `ids` or `count` should read
them off the live node, where they are correct and current.

**⚠️ Trap:** option 8. Lazy getters look like they give you everything for free
and quietly break the one property a snapshot exists to have.

## 2. `stored()` leaked its storage — fixed at the marker, not the traversal

**The problem.** `stored()` held the caller's `options` — including their
`storage` object — as an enumerable property. `unwrap` deep-copies a raw marker
by enumerating own keys, so any path where a raw marker reached a snapshot
carried the storage **contents** into `tree()`, `serialization()`,
`persistence()`, devtools and audit logs. Measured: top-level clean, nested in an
object clean, in a `Map` clean, **inside an array leaked**.

**Options considered (12).**

1. **Materialise markers inside arrays** so the raw marker never survives.
   Fixes the one path found; the leak returns with the next untraversed
   container. Also changes array semantics (see §3).
2. **Make `options` non-enumerable.** ← **chosen**
3. **Strip `options` in `unwrap`** when it sees a raw marker. Fixes `tree()` and
   nothing that reads the marker directly.
4. **Redact only `options.storage`,** keeping the rest enumerable. Requires
   knowing which fields are sensitive; the next option added to `StoredOptions`
   is sensitive by default and nobody remembers to add it to the list.
5. **Hold options in a `WeakMap` side table** keyed by marker. Equivalent
   privacy, plus a lookup and a lifetime question, for no gain over a
   non-enumerable property.
6. **Hold options in a closure** — requires the marker to be a function, which
   is the shape RFC 0008 already rejected for `stored()` (`unwrap` skips
   functions, so snapshots would silently lose the value).
7. **Resolve `storage` at marker-creation time** and keep only a resolved
   handle. Does not help: the handle is still the object.
8. **Freeze the marker.** Prevents mutation, not enumeration. Solves a different
   problem.
9. **Throw when `storage` is passed a non-standard object.** Breaks legitimate
   custom adapters, which are a supported feature.
10. **Warn when a raw marker reaches a snapshot** and leave the data. A warning
    that fires _after_ the secret is in the audit log.
11. **Symbol-key the options.** `unwrap` also copies own _symbol_ keys, so this
    changes nothing.
12. **Document "don't pass a storage object with secrets in it."** The default
    path was always safe; the failure is in a feature we shipped.

**Recommendation: option 2.** One line, O(1), no lifetime questions, and it
closes the _class_: `Object.keys`, spread, `JSON.stringify` and `unwrap` all skip
it on every path, including any not yet discovered. `createStoredSignal` reads
`marker.options` directly and is unaffected.

**⚠️ Trap:** option 1. "Fix the traversal that leaked" is the instinct, and it
closes exactly the paths you thought to test. 13.4.0 fixed two of them that way
and the array path stayed open for a release.

## 3. Markers inside arrays — warn rather than support or throw

**The problem.** A marker in an array is never materialised: `tree.$.list()[0]`
stays a raw `{ key, defaultValue }`, is not a signal, and writes to it are lost.
Silently.

**Options considered (12).**

1. **Warn at construction (ST2021).** ← **chosen**
2. **Throw at construction.** The value is unusable, so nobody depends on it
   working — but they may depend on the tree _constructing_. A throw turns a
   dormant modelling mistake into a boot failure on upgrade.
3. **Materialise markers inside arrays.** Makes the code work as written. Array
   elements would become signals, so `tree.$.list()` is no longer `T[]` — the
   type lies, and `map`/`filter` over it returns functions.
4. **Store arrays as `Map`s internally** so elements are traversable. This is
   what `entityMap` already is, and it wins 28.5× on the keyed-collection task.
   Applying it to _every_ array does not survive measurement: a per-node `Map`
   index cost **+12.1% on subtree reads and 310 B/node** in this repo (built,
   measured, reverted), index-keyed structures pay O(n) to reindex on any insert
   or reorder (Track D: `immutable.List.splice` is worse than a plain array at
   every size, 31.7 ms vs 806 µs at 1M), and `tree()` must hand back a real
   `Array` regardless. Most arrays in a tree are ordered lists of primitives.
5. **Support markers only in arrays that look like collections.** A heuristic
   deciding whether your array is "really" a collection.
6. **Type-level rejection** — make `T[]` containing a marker a compile error.
   Best-in-class if expressible; markers return `T`, so the array is
   `StoredMarker<T>[]` only before the brand is erased. Worth revisiting if the
   marker return types change; today the type system cannot see it.
7. **A lint rule.** Catches it in this repo, not in consumers.
8. **Silently drop markers from arrays.** Data loss instead of a broken value.
9. **Auto-convert an array of markers into an `entityMap`.** Guessing `selectId`
   and reordering the user's data.
10. **Runtime `Proxy` over array leaves** to materialise on access. Rejected for
    the same reason as lazy proxies generally (A5 in the optimisation survey):
    proxies defeat inline caching for every downstream reader, and the cost
    lands on code we do not control.
11. **Document only.** Documentation demonstrably does not prevent this class of
    mistake — our own demo shipped the array-leaf idiom while the entity
    cookbook sat in the repo.
12. **Do nothing.** It is silent data loss.

**Recommendation: option 1**, with the option-4 reasoning recorded at the
diagnostic so it is not re-litigated. A keyed collection is an `entityMap`; an
ordered list is an array leaf; a marker in an array is the first wearing the
second's clothes.

**⚠️ Trap:** option 3. Making it "work" produces a tree whose declared type is a
lie, which is worse than a value that is obviously broken.

## 4. Bundle budgets raised rather than reclaimed

**The problem.** ST2018, ST2020, ST2021, the `compared()` marker and the
`deepEqual` correctness fixes pushed the measured dev floor past its budget:
bare 6.99 KB against 6.9, entities 9.89 against 9.8, form 9.08 against 9.0.

**Options considered (12).**

1. **Raise the budgets with attribution.** ← **chosen**
2. **Shorten the diagnostic messages.** Done first, not instead: the ST2018 text
   originally inlined the full benchmark table into a `console.warn` and moving
   those numbers to the docs recovered 0.11 KB. The remainder is the diagnostics
   themselves.
3. **Move diagnostics behind a subpath import.** They fire during
   `signalTree()`, which every consumer calls; there is no import to gate them
   on.
4. **Ship diagnostics as a separate `@signaltree/diagnostics` package** applied
   as an enhancer. Real option, and it defeats the purpose: the developers who
   most need ST2018 are the ones who will not install a linter package.
5. **Drop the diagnostics.** ST2018 is worth ~30× and ST2021 catches silent data
   loss.
6. **Emit codes only** (`[ST2018]` with no prose) and put the text in docs.
   Saves most of the bytes and makes every warning a lookup. The message _is_
   the feature.
7. **Compress the strings** — a shared message table with placeholders. Saves
   perhaps a few hundred bytes at the cost of unreadable source and worse stack
   traces.
8. **Measure the budget with `ngDevMode: false`** so the gate tracks what
   consumers actually ship. Tempting, and it would have hidden this entirely —
   the point of an unfolded floor is to notice growth _before_ it stops folding.
   Changing the yardstick because you failed it is the wrong direction.
9. **Raise silently.** The failure mode this gate exists to prevent.
10. **Split the budget into dev and production lines,** tracking both. The best
    of the alternatives, and worth doing: `check-devmode-foldable` already
    measures the production number, so the data exists. Deferred as a follow-up
    rather than done under a release.
11. **Reclaim the bytes elsewhere** to stay under. Unrelated churn to hit a
    number.
12. **Fail the release.** It did — that is how this was found.

**Recommendation: option 1**, with option 2 applied first and the attribution
recorded inline: which module grew, by how much, and what it bought. The
production cost is **+0.37 KB**; the rest is dev-only text that folds, and
`check-devmode-foldable` confirms consumers reclaim ~1.67 KB per tree.

**⚠️ Trap:** option 8. Measuring only the folded bundle makes the gate green
forever and silently stops protecting the thing it was built for.

## Related finding, not a 13.6.0 change

A root partial write does **not** restore an entityMap:
`tree({ rows: snapshot.rows })` leaves the collection empty, while
`applyState(tree.$, snapshot)` restores it correctly. Verified identical in
13.5.0 and after the §1 change, so it is **pre-existing** and not caused by
either. Filed here so it is not mistaken for fallout from the snapshot-shape
change.
