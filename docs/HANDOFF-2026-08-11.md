**Stop re-litigating the thesis.** Four times now the instrumentation has been made more
honest — temporal drift, the clone confound, the undeclared margin, the missing isolating
arm — and each time the core idea stayed standing. That pattern is itself evidence. Further
architectural argument has low expected yield; the next real discoveries come from
**implementing and trying to falsify the ownership substrate**, starting with position
identity.

**Do not merge carriage into identity.** "An `ownerPath` string reaches the notifier"
and "a position identity survives `changeId`, re-materialization and restructuring" are
different claims with different proofs. Only the first has been demonstrated. An earlier
version of this ledger said "a stable ownership position can be resolved at write time —
yes", which over-claimed by exactly that gap.

**The instrument is now good, and the arms finally ask the question.** Interleaving by round
with a seeded per-round arm shuffle dropped the A/A floor from 20.35% to **0.06%** — a
300× improvement in resolution, and exactly the right fix. The harness can now resolve a
sub-percent difference, which it previously could not. That is real progress and it should
not be undersold.

The remaining distinction is now sharper, not muddier: the harness measures **two
different things** and they must stay separate.

**RETRACTED, and this is the important part.** An earlier revision of this section — and
of the ledger row above — read the +2.06% as "there is a real unused-owner cost of about
2%". **That attribution is wrong.** That comparison does not isolate what it is being asked
to isolate. The current harness now separates the two questions:

| arm                        | notifier                                                                                                       | notify arity | history               |
| -------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------ | --------------------- |
| `current-3arg`             | `Current3ArgPathNotifier` — a **class defined inside the benchmark** (`tools/bench-history-ownership.mjs:179`) | 3            | absent                |
| `owner-absent`             | the **real compiled `PathNotifier`** from `dist`                                                               | 3            | absent                |
| `owner-present-no-history` | real `PathNotifier`                                                                                            | 4            | absent                |
| `owner-history-inactive`   | real `PathNotifier`                                                                                            | 4            | **installed**         |
| `history-active`           | real `PathNotifier`                                                                                            | 4            | installed + recording |

Two consequences:

1. **Decision 20 is now measured on the right comparison.** `owner-present-no-history`
   and `owner-absent` use the same compiled `PathNotifier`, same build, same import, same
   JIT shape — differing only in whether `ownerPath` is passed while history stays absent.
   Latest full run: **+0.68%** median delta, CI **-0.51%..+2.24%**, A/A floor **0.18%**.
2. **The old +2.06% result survives only as a different measurement.** `current-3arg`
   vs `owner-absent` is still clone-vs-real and therefore belongs under the honest name
   **owner-capability structural overhead**. Latest full run there: **+1.91%** with CI
   **+0.76%..+3.03%**.

**The isolating arm is now present, which means the next choice is policy rather than instrumentation:**

```text
owner-absent               : new PathNotifier(),  ownerPath = undefined, installHistory = false
owner-present-no-history   : new PathNotifier(),  ownerPath = 'rows',    installHistory = false

unused-owner cost  =  owner-present-no-history  −  owner-absent
```

Same class, same import, same build, same JIT shape — differing only in the thing being
asked about. That question is finally real. What is still **not** settled is the policy:
keep decision 20 literal, or replace it with a declared budget.

Keep the existing old-vs-new comparison, but name it for what it measures —
**owner-capability structural overhead**: did making `PathNotifier` owner-capable slow its
ordinary three-argument path? For that question the strongest evidence is two _real builds_
(pre-owner commit vs owner-capable commit), not a hand-copied historical class.

Now that the isolating arm exists, there are three honest options: keep it literal and let
0A fail on performance; restate it as an
enforceable budget ("no material write-path regression; accepted equivalence budget ≤N%
under the canonical ownership benchmark"); or set a tighter budget than the measurement
supports. The second is the better _specification shape_ — "zero" is philosophically
attractive and statistically unenforceable — but **record why N**, or a future agent makes
an 8% implementation green by reconsidering the margin.

**Two claims, and only one of them is currently supported.** Keep them apart:

| claim                                                                     | supported?                                                                   |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| "We cannot detect any unused-owner overhead."                             | **Yes** — +0.68%, CI −0.51%..+2.24% includes zero, against a 0.18% A/A floor |
| "We have demonstrated overhead is below the amount we consider material." | **Not yet** — that needs a declared budget, and the budget does not exist    |

So do **not** pick a margin in order to make a badge turn green. Choose N from what
SignalTree considers an acceptable core write-path regression, then see whether the
evidence clears it. At **N = 5%** this run supports the claim comfortably. At **N = 3%**
it is encouraging but the upper bound of 2.24% leaves little headroom, and
machine-to-machine variation has not been characterised at all. At **N = 1%** the run does
not support it. The measurement is already useful without a badge; the badge is policy.

**The null result has a mechanism, which is why it is believable.** `PathNotifier.notify`
stores `ownerPath` **unconditionally** — there is no guard on whether any subscriber
observes owners:

```ts
this.pending.set(path, { newValue: value, oldValue: …, ownerPath, source });
```

So the timed `owner-present-no-history` arm genuinely performs the owner work on every
write with nobody consuming it, and it still does not register. That is a _stronger_ result
than a guarded implementation would give — the work happens and is undetectable, rather
than being skipped. The plausible reason is that the entry object is allocated per write
regardless, so one extra field on an existing object literal is close to free.

**Boundary on that result.** It measures the _unused_ path only. It says nothing about the
cost of threading owner through to a consumer once one exists — that is what
`owner-history-inactive` and `history-active` are for, and the active arm is the one with a
large, clearly resolvable cost.

**And it must be reproducible.** `EQUIVALENCE_MARGIN_PCT` defaults to `null` and no
committed script passes `--equivalence-pct`, so `npm run bench:history-ownership` reports
`INCONCLUSIVE` with reason `"no equivalence margin declared"`. The ±5% that produced a
PASS existed only in a shell invocation. Bake the declared margin into the script:

```json
"bench:history-ownership": "node --expose-gc tools/bench-history-ownership.mjs --equivalence-pct 5"
```

The margin is an architectural decision about acceptable write-path cost. It belongs in
the repo where it can be reviewed and changed deliberately, not in someone's history. A
figure no committed command reproduces is the same defect class as `numeric-claims`
checking that a number _names_ a generator rather than that the generator still _produces_
it.

### Traps that make a green run meaningless

These are not hypothetical; each one produced a false "pass" in recent history.

- **`nx test core` sets `passWithNoTests: true`.** Exit 0 does **not** mean tests ran.
  Nx also swallows the vitest reporter, so you see no counts. The only way to know the
  suite is live is to break something and confirm a non-zero exit.
- **Bare `npx vitest` from the repo root reports "no tests" for 175 files.** It picks up
  demo specs that fail to load without Nx's Angular setup. `--dir` and `--config` do not
  fix it. `nx test core` is the only valid runner.
- **A gate that passes is evidence of nothing** unless `--self-test` proves it can fail.
  Two gates were BLIND at the 14.0.0 release commit — passing while the thing they
  watched was broken. Both turned out to be real defects, not bad mutations.

## 3. What shipped in 14.1.1

Content is the audit release: retractions, naming cleanup, defects found while
auditing, and gates. Full detail in `CHANGELOG.md`, which also explains why a MINOR
carries a `BREAKING` section (14.0.0 was pulled; `13.x → 14.1.1` crosses the major
boundary, so no `^13.5.0` range resolves into the removals).

Two additions worth knowing about because they change how work gets verified:

**`spec-types` gate (new).** Spec files were typechecked by **nothing** —
`tsconfig.typecheck-all.json` excludes `**/*.spec.ts` and core's typecheck config
covers only `*.typing.spec.ts`. Vitest transpiles via esbuild, which strips types
without checking them. Consequence found in the wild: a test passed
`entityMap({ selectId, history })` after `history` was renamed to `recordHistory`, so
both arms of the test built an identical default tree and its assertion held
**vacuously**. Green suite, premise gone.

The gate is a **per-file ratchet**, not a clean check: turning it on cold reports 238
errors across 43 files, almost all test-idiom noise. Files may not get worse; a file
with no baseline entry must be clean. Pay it down with
`node tools/check-spec-types.mjs --update` (count may only decrease).

**Retention is now measured, not asserted.** `tools/bench-retention-arms.mjs` is
committed so every published figure has a runnable command.

```bash
node --expose-gc tools/bench-retention-arms.mjs <shape> <width> <steps> [norec]
#   shape: scalar | sameRow | diffRows | allRows | n<K> | mixed
```

At 50 entries over 50,000 rows, bit-stable across reps:

| what the writes touch        | retained                             |
| ---------------------------- | ------------------------------------ |
| scalar beside the collection | 0.300 MB                             |
| one row                      | **19.383 MB**                        |
| fifty _different_ rows       | **19.383 MB** — identical to one row |
| every row                    | **114.776 MB**                       |

Two facts that were wrong on every surface before this and are corrected now:

- `entries × width` is a **floor**, not the model. Its constant is **~8 bytes** (a
  64-bit pointer), not the ~10 previously published — which is why ST2029 said
  24.73 MB while the spike measured 19.58 MB, and nobody reconciled the two for two
  releases. The missing second term is **~40 bytes per _changed_ row**:
  `entries × (width × ~8 B + changedRows × ~40 B)`.
- `entityMap({ recordHistory: false })` makes retention **independent of collection
  width** — flat ~0.15 MB at 1k, 10k and 50k. It removes the width term rather than
  shrinking it. The old figures (0.18/1.25/5.61 MB) grew with width, which was wrong
  in kind, not degree.

A corollary worth carrying forward: **a large bulk operation is not inherently the
expensive history case.** One 400-row entry retains 0.434 MB.

The objective, restated because it is easy to slide back into the wrong one:

> Make multi-position optimistic operations safely reversible without caller-authored
> compensation. **User undo/redo is a second consumer of the same mechanism**, not the
> goal.

This is observed rather than assumed: v3's `bulkPatch$` deliberately performs no
optimistic pre-write, because there was no way to reverse a wrong bulk apply.

`commit()` splits into **`seal()`** (capture the speculative set) and **`confirm()`**
(promote into confirmed history). That split is what dissolves the
rollback/prefix-closure collision — prefix closure constrains _confirmed_ history, and
a sealed-but-unconfirmed turn was never subject to it.

### Phase 0 is two disposable spikes, and either can send the design back

**0A — ownership attribution.** Can a stable ownership position be resolved at write
time for plain leaves, `entityMap`, `form()`, `status()` and `stored()` with **no
measurable cost when history is not installed**? The benchmark now has six arms,
including an A/A control and the isolating `owner-present-no-history` arm, so the
current harness finally measures unused-owner cost directly. Also prove `PositionId`
stability across `changeId`, _and_ prove the naive derivation fails.

Head start: `entityMap` already computes `${basePath}.${id}`, so `basePath` **is** the
ownership position, free. The risk concentrates on the other four.

**Current state:** the owner-capable notify contract is now present in the working tree,
the benchmark exists at `tools/bench-history-ownership.mjs`, and `timeTravel()` now
records direct `form()` writes again; the mixed-tree regression where undoing a
neighbouring plain-leaf write rewound the form no longer reproduces. The benchmark has
also been tightened with an A/A control and bootstrap median-difference intervals, and
the latest full interleaved run now measures decision 20 on the right comparison:
`owner-present-no-history - owner-absent` on the same compiled `PathNotifier`.
Measured result: **+0.68%** with CI **-0.51%..+2.24%**, A/A floor **0.18%**. With no
declared equivalence margin, that remains **`INCONCLUSIVE`** by contract. What remains
from 0A is therefore partly policy and partly architectural: decide whether d20 stays
literal or becomes a justified budget, and decide how much ownership should become
first-class direct participation versus enhancer-local interception.

### The biggest remaining foundational risk is `PositionId`, not performance

**Do not let the benchmark's good news bury this.** It is more load-bearing than whether
passing an owner costs 0.7%.

What has been demonstrated:

```text
write  ->  ownerPath string
```

What has **not**:

```text
write  ->  stable semantic PositionId
             survives changeId / rekey
             survives re-materialization and restructuring
             remains valid inside turns retained long after the write
```

No `PositionId` abstraction exists, and 0A's required proof — that the _naive_ derivation
**fails** — has not been run against one. A path string is not an identity: `rows.7` means
whatever `7` currently designates, and `changeId(tempId, serverId)` is precisely the
operation that breaks that assumption. The whole turn store depends on the second form,
because a retained turn refers to positions long after the write that created it.

So the experimental question has narrowed usefully. It is no longer _"can this idea work?"_
It is now **"what exactly is a position identity, and where does it live?"** That is the
right question to enter Phase 1 on, and it is a genuine falsifier: if stable identity cannot
be made cheap across the seven write families, the architecture has a real problem that no
amount of rollback-semantics success compensates for.

### The first Phase 1 decision: where does ownership live?

**This matters more than the last 2% of the benchmark.** The benchmark is a gate; this is
a shape, and it decides what SignalTree becomes.

Only `entityMap` participates in the notifier directly. The other six families surface
ownership through `interceptLeafSignals`, which `timeTravel()` installs. So the sentence
the architecture is written around —

> The tree defines ownership.

— is not yet true. Today it is:

> The tree can expose ownership **once the appropriate interception machinery has been
> installed**.

That is materially weaker, and it matters because the intended consumers are wider than
one enhancer: transactional rollback, user undo, provenance, diagnostics, agent
attribution, auditing. If each must depend on or recreate the interception layer, then
ownership is not substrate — it is an enhancer implementation detail that several features
happen to need. That is the seam that gets expensive later.

**Neither A nor B is automatically wrong. The requirement is that the choice be explicit.**

|                  | **A — intrinsic**                                                                                                                                                            | **B — intercepted**                                                                                                                                              |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner comes from | the mutating primitive emits it                                                                                                                                              | a history-capable enhancer infers/supplies it                                                                                                                    |
| Gains            | history decoupled from `timeTravel()`; transactions, provenance and agent tooling share one substrate; one definition of owner; true even with no history enhancer installed | less disturbance to core hot paths; machinery exists only when installed; helps decision 20                                                                      |
| Costs            | touches more mutation paths; more potential hot-path work; markers need a clean way to carry semantic position                                                               | every consumer depends on the interception subsystem or silently misses writes; enhancer siting becomes correctness-critical; some mutation routes can bypass it |

**C — the hybrid, and the one to try hardest to falsify first.** Do not assume the answer
is "make all seven direct". Separate the two questions the enhancer currently answers
together:

```text
Who owns this write?        <- intrinsic to the materialized position
Should anyone observe it?   <- lazily installed by a consumer

materialized marker
   └── stable PositionId / owner identity          (always known, cheap)

mutation
   └── observer installed?
          no  -> ordinary write, nothing emitted
          yes -> emit path/before/after + the EXISTING owner
```

A marker can know its own stable position identity cheaply without notifying anything
when no observer exists. The history subsystem then installs the _observation_ path but
does **not invent** ownership. That keeps "the tree defines ownership" true while leaving
the zero-when-unused story available, and it is a different architecture from today's,
where the enhancer both sees the write _and_ supplies the semantic owner.

Two separable things decide it:

- **The benchmark** says whether the separation is cheap enough — now that the floor is
  0.06%, it can finally answer that.
- **The code** says whether the six conditional families can carry their own position
  identity without re-implementing interception in six places.

### Benchmark: one recommendation still outstanding

Interleaving and seeded per-round arm shuffling landed, and they are what collapsed the
floor. The third change did not:

**Bootstrap the PAIRED differences, not two independent bags.** Samples are now
round-aligned, so `delta[r] = candidate[r] − baseline[r]` shares each round's machine
state. Resampling those deltas removes the drift term instead of averaging over it.
`bootstrapMedianDiff(left, right)` still resamples the two arrays independently, which
discards the pairing the interleaving just created. The current CI is therefore
**conservative rather than wrong** — a paired analysis would tighten the current
decision-20 CI (**-0.51%..+2.24%**) further, which is exactly what you want when the
question is whether a sub-1% median delta is real.

Also: **do not raise `--batches` to chase resolution.** A longer run gives drift longer to
accumulate; that is what kept the relative floor flat at ~20% when the workload went up 9×.

### Rule: a disposable prototype may not live under a published source glob

`packages/core/src/lib/internals/rollback-viability-prototype.ts` already emits
`dist/packages/core/src/lib/internals/rollback-viability-prototype.d.ts`, and core's
`files` includes `src/**/*.d.ts` relative to the publish root. So
`PrototypeRollbackResult`, `PrototypeRollbackStatus`, `PrototypeScalarWrite` and
`PrototypeCollectionRemove` would ship as public types in the next tarball;
`dead-exports` already lists them.

Once those names ship, a research artifact becomes compatibility surface. Spikes go in
`tools/spikes/` or another path outside the build and package surface — or the semantic
result gets written down and the prototype is deleted immediately. "Disposable" has to
mean disposable in the only sense that matters: it cannot reach a consumer.

### Audit the other harnesses, but narrowly

The drift is a property of this machine, not of one benchmark: **elapsed position in a
sequential run materially changes observed throughput.** So any comparative harness shaped
`AAAA…BBBB…` rather than `ABBA…` deserves inspection. Two cases, and they do not deserve
equal effort:

- **Absolute timing claims** (e.g. "undo at 50k ≈ 436 µs"). Drift inflates variance, but a
  large, independently reproduced, clearly-scaling result can be perfectly sound. Low
  priority.
- **Comparative small-delta claims** (e.g. "B is 3% faster than A", published slopes and
  `343×`-style multiples). Blocked sampling is potentially fatal here. **This is where to
  look.**

Search for blocked comparative arms first, and only re-run the load-bearing percentages.
This has not been done and no existing figure is being called wrong on this basis.

**0B — rollback viability.** The hierarchy doc's six outcome cases are now backed by
an executable prototype at
`packages/core/scripts/rollback-viability-prototype.ts` with focused spec coverage
in `packages/core/src/lib/rollback-viability-prototype.spec.ts`.
**Case 4 (structural collection mutation under a concurrent writer) was the required
anchor and is now exercised both ways**: the prototype can reinsert a removed row when
the surrounding anchors still bracket a valid slot, and it reports
`cannot-reconcile` when a concurrent reorder destroys that bracket. That is the 0B
result to carry forward: scalar rollback has a supersession answer; structural
rollback needs collection anchors and an explicit failure mode.

Do not blur that with current user undo semantics: a focused regression now proves
that snapshot `timeTravel()` undo restores a simple `removeOne` at the original
position. The remaining anchors problem is the speculative/concurrent case, not the
single-user snapshot undo path.

### The evidence boundary you must not cross

The retention numbers in §3 measure **`timeTravel()`'s snapshot stack**. The proposed
turn store is a different data structure — one entry per attributed write, so a 400-row
operation is ~400 entries and is plausibly `O(entries)`, not `O(turns)`. **That has not
been measured.** Phase 2 carries a turns×rows matrix to measure it.

Turns are the retention unit **because they are indivisible**, an architectural
argument that needs no memory evidence. Memory limits decide how many turns fit, not
whether a turn can be cut apart. An earlier revision of the hierarchy doc claimed the
turn-based retention was "now measured" — it measured the wrong structure. Don't
re-derive that mistake.

## 6. Failure patterns from this session — expect to meet them again

Recorded because they cost real time and two of them shipped to npm.

**A correct fix placed where something downstream silently undoes it.** Three
instances, all found within an hour:

- `publish-all.sh` resolved `workspace:*` specs **once before** the publish loop, and
  `publish_package()` runs `nx build` per package, which regenerates the dist manifest
  and overwrote the resolution. The fix was present, documented, and had never once
  worked — **14.1.0 shipped broken because of it.** Now resolved after each build,
  immediately before `npm publish`, with an independent guard on the bytes being
  shipped.
- `release-claims` excluded only prereleases matching `v${current}-`, so the fix worked
  for 14.0.0 and the bug returned at the next release. Now excludes all prereleases.
- `angular-compat` matched `from '...'` with single quotes only against **minified**
  output (`from"./core/ng-forms.js"`), so its reachability walk never left the entry
  file — while advertising itself as transitive. Now 150 reachable files, not 16.

**Verifying the mechanism instead of the outcome.** The 14.1.0 publish dry-ran clean
and printed six successes; the packages were unusable. Only reading the **registry**
afterward caught it. For anything outward-facing, verify the artifact where consumers
see it, not the tool's own report.

**Blind global replaces.** A `map` → `asMap` sweep left `llms.txt` and the core skill
saying `asMap()` was _"renamed from `asMap()`"_ — renamed from itself. A later
`15.0.0` → `14.1.0` → `14.1.1` sweep rewrote freshly-written comments into false claims
about which version shipped a bug. Both caught, both the same hazard. Scope replaces to
the files you have read.

**Numbers changed without re-running them.** Retention figures were once "reconciled"
by picking the pair that had a published table, without executing anything. When
actually run, the original number was closer than the edit. If a figure changes, the
harness runs.

## 7. Conventions

- **No RFCs for our own work.** `TODO.md` holds decided-but-undone work; `docs/rfcs/` is
  an archive of decisions already taken, kept mainly for the options that were
  _rejected_ and why. An RFC is what an outside contributor writes.
- **Point-in-time documents get correction notes, not rewrites.** Dated audits under
  `docs/audits/<month>/` and research under `docs/research/` record what was believed
  then. Add a dated correction block; do not edit the original claim.
- **Commit messages say _why_.** Recent history is the model.
- **No Claude attribution lines in commits.**
