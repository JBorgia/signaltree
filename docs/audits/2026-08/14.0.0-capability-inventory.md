## 0. Method, and what "verified" means here

Every row below was checked against the working tree at `b254edc1`. Rows carry an
evidence tier, and the tiers are kept apart deliberately because they are not the
same kind of claim:

| tier     | meaning                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------- |
| **SRC**  | The symbol/behaviour was read in the shipping source at the cited `file:line`.                          |
| **SPEC** | A test pins it. The spec file exists at the cited path; it was not re-run for this audit.               |
| **DOC**  | The claim is asserted in `CHANGELOG.md` or a design doc. **A measurement in this tier was NOT re-run.** |
| **GREP** | Demo coverage, established by searching `apps/demo/src` excluding `*.spec.*`.                           |

**What this audit did NOT do:** it did not re-run a single benchmark. Every
number in this document — 75x, 4.9x, 4,368 µs → 78 µs, 7x/160x, 3.32 MB — is
reproduced from `CHANGELOG.md` and is tier **DOC**. Where a number is load-bearing
for a demo claim it is flagged ⚠️, because a demo that puts a number on screen is
making a stronger promise than a changelog entry does.

## 1. The architecture the release is about

[`materialisation-prior-art.md` §1](../../architecture/materialisation-prior-art.md)
names what SignalTree is, precisely:

> **Demand-driven incremental view maintenance over a reactive dependency graph**,
> with per-node memoisation, structural sharing, and a per-marker snapshot/hydrate contract.

Six mechanisms implement it. This is the spine of the inventory, because 14.0.0
is not a grab-bag — almost every change lands on one of these six, and the ones
that don't are packaging.

| #   | mechanism               | implementation                                                               | verified                                                         |
| --- | ----------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| M1  | **The view**            | `tree()` — a plain object materialised from the signal graph                 | SRC                                                              |
| M2  | **Incremental refresh** | one `computed` per node in a `WeakMap`, invalidated by Angular's graph       | SRC `lib/internals/materialize-markers.ts:119` (`SNAPSHOT_MEMO`) |
| M3  | **Structural sharing**  | a clean subtree returns BY REFERENCE; a one-leaf write rebuilds O(depth)     | SPEC `lib/snapshot-aliasing.spec.ts`                             |
| M4  | **Demand-driven**       | the `computed` is created lazily; a node never read allocates nothing        | SRC `materialize-markers.ts:128`                                 |
| M5  | **Per-node contract**   | markers declare `snapshot` / `hydrate` / `transient` on the registry         | SRC `materialize-markers.ts:47-53`                               |
| M6  | **Restore semantics**   | `HydrateMode = 'merge' \| 'restore' \| 'rehydrate'`, chosen by the call site | SRC `materialize-markers.ts:45`                                  |

**The one-sentence thesis of 14.0.0:** _a snapshot carries state; anything
recomputable is structure, and structure does not belong in a payload._ M5 and M6
are where the release did most of its work — they did not exist as a stated
contract before it.

⚠️ **Correction already absorbed:** the architecture doc previously described an
`owns()` hook on the marker registry. **There is no `owns` hook.** The contract is
`check` / `create` / `snapshot` / `hydrate` / `transient` (verified SRC,
`materialize-markers.ts:47-53`). Ownership is decided inside each marker's
`hydrate`, which receives the mode. Do not put `owns()` on a demo slide.

| A3  | `activeId: Signal<K \| undefined>`     | SRC `entity-signal.ts:196`, type `types.ts:877` · same SPEC                                                 | **none**        |
| A4  | `activeEntity: Signal<E \| undefined>` | SRC `entity-signal.ts:505`, type `types.ts:878` · same SPEC                                                 | **none**        |
| A5  | `setActiveId(id)`                      | SRC `entity-signal.ts:513`, type `types.ts:879`                                                             | **none**        |
| A6  | `clearActiveId()`                      | SRC `entity-signal.ts:520`, type `types.ts:880`                                                             | **none**        |
| A7  | `changeId(from, to)`                   | SRC `entity-signal.ts:653`, type `types.ts:896` · same SPEC                                                 | **none**        |

**Why A3/A4 are not sugar** (SRC comment, `types.ts:874`): `activeEntity` resolves
through `byId`, so it is O(1) and invalidates only when _that_ entity changes. A
hand-rolled `computed(() => all().find(r => r.id === activeId()))` recomputes on
every collection change. That is the M2 argument — incremental refresh at the
right granularity — and it is the demo-able difference.

**A7 states its own limitation** (SRC `entity-signal.ts:653` region): a node
already _held_ from the old id resolves to `undefined`, because a node closes over
its id and aliasing the old key would let a later `addOne({ id: oldId })` share
one signal between two entities.

**A1/A2 is the only capability every competitor had and SignalTree did not** (DOC).

### 2.3 Observability seams (M5, M6)

| #   | API                                                          | evidence                                                                                             | demo     |
| --- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | -------- |
| A12 | `onTreeError(listener)` — `@signaltree/core/authoring`       | SRC `authoring.ts:71`, impl `lib/internals/error-reporter.ts:60` · SPEC `lib/error-reporter.spec.ts` | **none** |
| A13 | `onHydrateDecision(listener)` — `@signaltree/core/authoring` | SRC `authoring.ts:38`, impl `materialize-markers.ts:221` · SPEC `lib/hydrate-decisions.spec.ts`      | **none** |

**A12** is one place to observe every error the library catches; the JSDoc example
in source is literally a Sentry call (SRC `error-reporter.ts:52-54`). Markers still
handle their own errors as before — this is additive. A throwing listener cannot
damage the reporting operation, and is itself reported as **ST2025**
(SRC `error-reporter.ts:84`).

**A13** observes when a marker _declines_ a rehydrate payload or _normalises_ one.
Two design details, both verified SRC:

- The `reason` is a stable machine-readable union, `'loader-owns-source' | 'no-request-survives-boundary'`
  (`materialize-markers.ts:180-182`), emitted from three sites: `entity-map.ts:341`,
  `async-source.ts:171`, `status.ts:208`.
- It is **not** a warning, deliberately: declining is correct behaviour, and
  warning on correct behaviour trains people to ignore the channel.
- Listeners fire **in production**. An earlier revision guarded the whole call
  site to keep the prose out of the bundle, which made it a public API that
  silently did nothing in a production build — the exact defect class this
  release removed `tree.$.count(5)` for. Reverted, and pinned by a test whose name
  says so (DOC + SPEC).

### 2.4 Enterprise folded into core

| #   | API                                       | evidence                                                                                              | demo                                                                                |
| --- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| A14 | `tree.updateAndReport(updates): string[]` | SRC `lib/signal-tree.ts:1079` (defined), `:1365` (forwarded through builder), type `lib/types.ts:312` | `index.html`, `home.component.html`, `benchmark-orchestrator.component.html` (GREP) |

Replaces `enterprise().updateOptimized()`: no enhancer, no bundle. The reason is
measured, not stylistic (DOC): the diff engine was **slower than the thing it was
meant to beat** — ~7x at 2,000 leaves with 10% changed, ~160x when all change —
because core leaves are `signal(value, { equal })` with a reference-equality
short-circuit, so the writes the diff engine walked the tree to skip were already
no-ops. It also silently dropped writes targeting arrays, never fixed. ⚠️ these
two multipliers are DOC-tier.

## 5. Security

| #   | fix                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | evidence                                                                                                                                                                                                                                | demo     |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| S1  | **`stored()` could leak its storage into any snapshot.** The marker held the caller's `options` — including their `storage` object — as an **enumerable** property, and `unwrap` deep-copies a raw marker by enumerating own keys. So wherever a raw marker reached a snapshot it carried the CONTENTS of that storage into `tree()`, and from there into `serialization()`, `persistence()`, devtools payloads and audit logs (e.g. an `auth-token` JWT). 13.4.0 closed the top-level and nested-object routes; **a marker inside an array still escaped, because array elements are never traversed.** `options` is now non-enumerable, so the payload is invisible to enumeration on every path — _including any not yet found._ `createStoredSignal` reads it directly and is unaffected. | SRC `lib/markers/stored.ts:473-478` (`Object.defineProperty(marker, 'options', { enumerable: false, writable: false })`) · SPEC `lib/markers/stored-leak.spec.ts` (verified on five paths plus a plain object spread) · RFC 0008 item 1 | **none** |

This is the highest-severity item in the release and has **zero demo presence**.
It is also the one item where a demo is arguably the wrong medium — a page that
shows a leaked JWT is a page that teaches the attack. Recommend a prose callout,
not an interactive demo.

All are dev-only and fold out of production builds. All verified SRC.

## 7. Breaking changes

| #   | break                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | evidence                                                                                                                                                                                                                             |

| B1  | **Calling a leaf is no longer a setter.** `tree.$.count(5)` is a compile error; the `(value: NotFn<T>): void` and updater overloads are gone from `CallableWritableSignal<T>`. **It never worked** — a leaf **is** a real Angular signal, and calling a signal is a READ that discards its argument. Measured: `tree.$.count(5)` on a leaf holding `0` returned `0` and left it at `0`. The same expression one level up (`tree.$.user({name:'Bob'})`) does work, because a branch is SignalTree's own accessor. So the type promised a uniformity the runtime never had, and the failure was invisible **at compile time AND at run time** — which is why this is a removal, not a deprecation. Branches and the root remain callable. Making it true at runtime was measured and **rejected on IDENTITY, not speed**: a callable wrapper costs ~4% on a set+get (inside noise), but `isSignal()` returns `false` for it and `Symbol(SIGNAL)` is absent, so `toObservable`, `model()`/`input()` interop and everything guarding on `isSignal` would break. **The structural reason for the gap, and it is a real one:** the `demo-coverage`
gate holds the **root barrel** — top-level exports of `@signaltree/core`. Every
item in the 0/N rows above is either a **method on a node** (`tree.$.rows.prependOne`),
a **method on an enhanced tree** (`tree.pauseRecording`), a **type**, or an
**`/authoring` export**. None of those are root-barrel exports, so none are in the
gate's domain. The gate is not broken — it proves exactly what it claims. It just
does not reach the surface this release added to.

That is the finding: **14.0.0's new capability lives almost entirely outside the
one automated check that would have noticed it missing from the demo.**

The demo's What's New page ([`whats-new.component.html`](../../../apps/demo/src/app/examples/features/fundamentals/examples/whats-new/whats-new.component.html))
does carry a substantial 14.0.0 section — the thesis, B1, B2, B5, B6, F2, F5, C1,
C2, S1, ST2020–ST2023 and the marker contract (A22–A23). What it omits: every
item in §2.1–§2.5, ST2024–ST2026, F1's zoneless consequence, F3, F4, F6, F7, F8,
C3, C4, and B3/B4.
