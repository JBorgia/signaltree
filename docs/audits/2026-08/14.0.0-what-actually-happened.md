# 14.0.0: the complete ledger

**Status:** disclosure record, 2026-08-10. Written because the findings were
reported one at a time across a very long session, which is not the same as being
communicated. This is all of it in one place, generated from git rather than
recalled.

**Next release target: 14.1.0.**

## The headline judgement error

**79 commits landed between `v14.0.0-rc.1` and `v14.0.0`.** That is not a release
candidate being confirmed; that is an audit running at full speed into a publish.

I published while I was still actively finding defects, and I kept finding
significant ones afterwards — the recording semantics, the `shouldSkip` design
error, four wrong RFC statuses. I raised holding once and then published when
asked. I should have pushed back harder: the correct advice was "this audit is
still producing findings, so the version is not stable enough to freeze," and I
did not give it plainly enough.

### Retracted, 2026-08-10: the two defects I reported here first do not exist

This table originally led with "collection mutations create no history entry, so
structural undo does not work" and its claimed consequence, "undo can revert a change
the user never made." **Both were my error, and neither is true.**

`PathNotifier` batches through `queueMicrotask` and `timeTravel()` records on
`onFlush`, so **no** marker write records synchronously. I asserted
`getHistory().length` and `canUndo()` in the same tick as the mutation, got 1 and
`false`, and reported a missing feature. After one tick the entry is there. Verified
by outcome rather than by counter:

| Operation                              | After `undo()`                     |
| -------------------------------------- | ---------------------------------- |
| `removeOne('c')` on `a,b,c`            | `a,b,c` — the row comes back       |
| `updateOne('a', { n: 99 })` from `n:1` | `n:1`                              |
| `setAll` reorder `a,b,c` → `c,a,b`     | `a,b,c` — **order** restored too   |
| 20 `updateOne` in one microtask        | one entry, one undo reverts all 20 |

This is the exact failure this document names in "Process failures" #4 — **asserting
the mechanism instead of the outcome** — committed in the act of writing the document
that names it. I checked a counter and never once called `undo()`.

What follows from the retraction: TODO item 2a is not "record collection mutations,"
it is a much smaller fix; the fit-page rewording in item 4 was justified by a
drag-undo failure that does not reproduce; and the six audit verdicts scored on the
old premise need re-scoring, not just case 8.

## Process failures worth naming separately

These are not defects in the product; they are ways I produced unreliable output.

1. **Committed or pushed with red gates three times.** Each time I had just run the
   check and not read it.
2. **Read `$?` off a pipe twice**, getting `tail`'s exit code instead of the tool's.
   Once produced a false "FORMAT CLEAN".
3. **Published a benchmark artifact.** A `0.176 µs/write` figure that was dead-code
   elimination — nothing read the state back. The real number is ~220 µs. I nearly
   shipped it because it looked plausible.
4. **Tests that passed for the wrong reason**, three times: a reorder check with no
   `sortComparer` (the field was inert), an `undo` check that never exercised undo,
   and a spec asserting `tree.undo()` returns `true` when it returns void.
5. **Counted a proxy instead of comparing sets** — 27 documented ST2xxx codes
   against 27 in source read as clean, while ST1031 and ST1032 were emittable and
   undocumented.

The pattern in all five: verifying the _mechanism_ rather than the _outcome_.

## What I am changing about how I work here

1. **Read the result of every check before committing.** No exceptions, and never
   in the same command as a formatter that rewrites files.
2. **Assert outcomes, not mechanisms.** A postcondition that a caller could satisfy
   without the behaviour under test is not a postcondition.
3. **Distrust a flattering number harder than an unflattering one.** Both artifacts
   I nearly published made us look better.
4. **Do not freeze a version while an audit is still producing findings** — and say
   so plainly rather than deferring to urgency.
